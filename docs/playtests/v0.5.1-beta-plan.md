# v0.5.1 Five-Person Local Beta Plan

- Status: Active
- Milestone: `v0.5.1 Polish and Local Beta`
- Tracking issue: #103
- Related: ADR-0007, #82, #98, #99, #100, #101, #102, #107, #108

## Purpose

This plan defines how the first five-person beta is set up, how feedback is
collected, how defects are classified, and when the beta is considered complete.
It keeps the beta local and private: no public ingress, no Oracle cluster, no paid
VPS, and no payments.

## Scope

### In scope

- A private Android beta for five known testers.
- The backend running on the development PC and reachable over Tailscale.
- Real accounts, cloud saves, save conflicts, leaderboards, telemetry choices,
  and remote config.
- Phone and tablet layouts in landscape orientation.
- Feedback capture, defect triage, and polish follow-up.

### Out of scope

- Public launch, marketing, or app-store submission.
- Oracle provisioning, a paid VPS, or any paid cloud resource.
- Payments, premium currency, Cores, or monetization.
- Localization beyond English.
- Co-op or multiplayer.

## Public repository handling

The repository is public even though the beta itself is private. Raw feedback,
tester identities, account names, device serial numbers, screenshots that show
account data, and raw `logcat` must stay in a private beta channel. Only
non-identifying, redacted summaries and evidence are committed. Personal data is
never written into a public issue, pull request, commit, or screenshot.

## Beta shape

| Item | Value |
|---|---|
| Testers | Five known people |
| Build | Version `0.5.1`, recorded in #107 |
| Backend | Local services on the development PC |
| Network | Tailscale private network only |
| Devices | At least one phone and one tablet |
| Minimum Android | API 26 (Android 8.0) |
| Orientation | Landscape |
| Telemetry | Off by default, opt-in per tester |
| Duration | Three completed runs per tester, plus feedback |
| Support window | One scheduled check-in per week while the beta is active |

Testers are identified by a pseudonymous tester ID in any public summary. Real
names, account names, device serials, tokens, and save contents are not committed
to the repository.

## Tester setup

1. Receive the versioned APK and its SHA-256 checksum from #107.
2. Join the dedicated Tailscale network and confirm the beta host is reachable.
3. Install the APK and confirm the in-game version matches `0.5.1`.
4. Register a beta account with a unique username. Do not reuse a personal
   password.
5. Complete three runs across at least one phone and one tablet layout when
   available.
6. Exercise cloud save backup, restore, and both conflict choices at least once.
7. Choose whether to enable telemetry. Leaving it off is fully supported.
8. Submit feedback with the template in `docs/playtests/beta-feedback-template.md`
   through the private beta channel. Do not post raw feedback to the public
   issue tracker.
9. Uninstall the beta build when the beta ends or when asked to leave.

## Privacy and data handling

- Accounts contain a username and a password hash. Passwords are never logged.
- Cloud saves contain game progression only. No contact data is required.
- Telemetry is opt-in and defaults to off. Opted-out clients send no telemetry.
  Raw telemetry events are retained for 30 days by the worker described in
  ADR-0006.
- Server logs and private feedback must not contain access tokens, refresh
  tokens, passwords, save documents, device serials, or personal data.
- Only redacted, non-identifying screenshots and `logcat` excerpts are committed
  to this public repository.
- Raw feedback and tester identities stay in the private beta channel and are
  retained until the beta exits or the tester asks for deletion. A tester may
  also request deletion of their beta account and associated saves. The deletion
  is performed through the procedure recorded by #108 and confirmed to the
  tester.
- Public summaries contain no personal data. Because Git history cannot be
  rewritten safely, personal data is never committed in the first place.
- Testers are told which data is stored, why it is stored, where feedback is
  kept, and how to leave the beta.
- Personal data is not sold, shared, or used for advertising.

## Feedback loop

- Testers submit feedback with `docs/playtests/beta-feedback-template.md` through
  the private beta channel.
- The beta lead removes personal data and creates a redacted public issue or
  beta record when follow-up is needed. Defects use the existing bug issue form
  after redaction.
- The beta lead triages new reports within three business days while the beta is
  active.
- Defects receive severity labels and, when actionable, a follow-up issue linked
  to this milestone or the next one.
- Feedback is grouped by theme before tuning work in #98.
- A short weekly summary records new reports, fixes, open risks, and the next
  check-in. It contains no personal data.

## Severity definitions

| Severity | Definition | Examples | Target response |
|---|---|---|---|
| P0 | Beta cannot be used, data is lost, or a security issue is exposed. | Crash on launch, account takeover, persistent progression deleted, public exposure of a private service | Stop the beta, fix or roll back, notify testers |
| P1 | A core beta flow is broken with no acceptable workaround. | Cannot sign in, cloud save always conflicts, leaderboard submission always fails, telemetry cannot be disabled | Fix before beta exit |
| P2 | A feature is degraded but a workaround exists. | Occasional UI overlap, one reward option mispriced, intermittent retry | Fix or schedule before exit |
| P3 | Polish, wording, or minor visual issue. | Spacing, inconsistent audio cue, unclear label | Triage and schedule after the core exit criteria |

A defect with no reproduction steps, build version, or device details is
returned to the tester for more information before it is prioritized.

## Beta exit criteria

The beta exits only when every item below is true or has an explicit, reviewed
exception recorded in this document.

### Onboarding and participation

- [ ] Five testers have installed the `0.5.1` build and signed in.
- [ ] Each tester has completed at least three runs.
- [ ] At least one phone and one tablet have produced device evidence.

### Stability

- [ ] No open P0 defect.
- [ ] No open P1 defect without an accepted workaround and a scheduled fix.
- [ ] Beta sessions show no `FATAL EXCEPTION`, `AndroidRuntime` crash, or
      `NullReferenceException` in the reviewed `logcat` samples.
- [ ] No unresolved data-loss report.

### Online flow

- [ ] #82 passes the full online flow on Android against the local backend.
- [ ] Registration, sign-in, refresh, and sign-out work for testers.
- [ ] Cloud save backup and restore work, and both conflict choices are
      exercised.
- [ ] A completed run appears on the highest-round leaderboard.
- [ ] Telemetry stays silent when disabled and produces an aggregate when
      enabled.
- [ ] Remote config can enable and disable cloud saves, leaderboards, and
      telemetry without rebuilding the APK.

### Data safety

- [ ] #102 recovery scenarios pass on device.
- [ ] No tester lost persistent progression during the beta.
- [ ] Interrupted writes, corrupt saves, offline transitions, and app restart
      preserve a consistent revision.

### Performance and polish

- [ ] #99 records at least one physical phone and one tablet measurement.
- [ ] The game holds the agreed beta frame target on the measured devices. The
      current target is a 30 FPS floor with a 60 FPS goal, no unbounded memory
      growth in a 10-minute run, and a cold start within 10 seconds on the
      measured device. The target follows the Android configuration in
      `docs/setup/unity.md` and the profiling evidence required by
      `docs/agents/review-checklist.md`.
- [ ] #100 completes the safe-area, touch-target, audio, and feedback pass.
- [ ] No user-facing string is added without a localization key.
- [ ] Audio can be muted and the choice persists.

### Process

- [ ] #108 records the public-Internet probe, the Tailscale ACL and Funnel
      checks, and the BFF peer reachability in the security checklist before
      testers connect. Until then, #108 stays open as a pre-beta gate.
- [ ] #107 records the build version, checksum, and install evidence.
- [ ] All beta feedback is triaged.
- [ ] The #98 tuning note records what changed and what still needs validation.
- [ ] The beta record states that payments, premium currency, and localization
      remain out of scope.

The network, secret, log, tester-data, and dependency review for this beta is
recorded in `docs/playtests/v0.5.1-local-beta-security-checklist.md`.

## Local versus VPS decision rule

The beta stays local by default. A VPS is considered only when at least one
concrete trigger from ADR-0007 exists:

- testers need availability while the development machine is off;
- the beta needs a stable public URL;
- realistic latency, backups, or deployment evidence is required;
- Oracle capacity remains unavailable and the local beta is complete.

If a trigger appears, the project writes an ADR that selects the provider,
architecture, image platform, backup plan, TLS, and least-privilege access. A
follow-up issue is created. No VPS or paid resource is provisioned without an
accepted ADR and explicit approval. The v0.5.1 milestone does not include VPS
deployment.

## Roles

| Role | Responsibility |
|---|---|
| Beta lead | Triage, weekly summary, exit decision, tester communication |
| Backend host | Local services, Tailscale access, backups, remote config |
| Tester | Install, play three runs, exercise online flows, submit feedback |
| Maintainer | Fix accepted defects and update the changelog |

## Evidence

- Raw feedback, device serials, account data, and unredacted `logcat` stay in the
  private beta channel. They are not committed to this public repository.
- Only redacted, non-identifying evidence is stored under
  `docs/playtests/evidence/`.
- Every public record includes build version, commit, device or emulator model,
  Android version, date, checks performed, defects, and verdict.
- Emulator results are labelled as emulator results. Physical device results
  are labelled with the actual model.
- Human playtesting is claimed only when a human actually performed it. Use
  truthful wording such as "automated verification" or "tester-reported" when
  that is what happened.
- Raw profiler traces, APKs, keystores, tokens, passwords, and save documents
  are never committed.
